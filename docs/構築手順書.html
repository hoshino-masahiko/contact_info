緊急連絡先登録ポータル構築手順書

今回の環境をゼロから作る場合の、実行コマンドと「コンソールでどこを見れば確認できるか」をステージ順に並べたものです。すでに稼働中の環境（下記IDはすべて実在の値）をコンソールで辿って答え合わせする使い方もできます。

構成の全体像・用語の説明は 従業員ポータル構成台帳 を参照してください。

この手順書のコマンドを、この文書に書かれているのと同じスタック名・同じドメイン名のまま同じAWSアカウントで再実行すると、エラーになります。Stage 1〜4で作成済みのスタックとドメイン委任が既に存在するためです。実際に手を動かして新しい環境を再現したい場合は、別のスタック名または別ドメインを使ってください。「現在稼働中のportal.tokaiec.co.jpの環境が、この手順書の通りに構築されているか」をコンソールで照合するだけであれば、各ステップの「コンソールで確認」欄だけを辿れば十分です。

CloudFormationは何を、どう作るか

Stage 1・3・4はどれも同じaws cloudformation deployを実行していますが、そのたびに何が起きているかは共通です。

  1. 手元のPCからaws cloudformation deployでテンプレート（yaml）をCloudFormationサービスに送る
  2. CloudFormationサービスがyamlを読み、書かれているリソースの依存関係を解析する
  3. 依存関係の順番に沿って、各リソースに対応するAWSサービスのAPIを直接呼び出す（例: DynamoDBならDynamoDBのAPI、LambdaならLambdaのAPI）
  4. 全リソースの作成が完了したらスタックがCREATE_COMPLETEになる。途中で失敗したら自動でロールバックする

ここにLambdaが介在する工程はありません。Stage 4で作られる4つのLambda関数（Get/UpdateEmployeeFunction・Import/ExportCsvFunction）は、この処理の結果として作られる成果物であり、デプロイを実行する側ではありません。デプロイが終わったあと、従業員がログインしたりCSVをアップロードしたりした時に初めて動き出します。

    コンソールで確認: 権限を持っているか

    「AWSアカウント」とは、AWSの利用契約の単位であり、12桁のアカウントID（このプロジェクトでは018811607892）で識別されます。1つのAWSアカウントの中に、複数のIAMユーザーやIAMロール（実際に操作を行う認証情報の単位）を作成できます。このデプロイ作業を行う前に、自分が使っているIAMユーザーまたはIAMロールに、次のAWSサービスに対する操作権限が付与されているかを確認してください。

    • CloudFormation（スタックの作成・更新・削除）
    • IAM（Lambda関数が使うIAMロールの作成）
    • S3（バケットの作成、ファイルのアップロード）
    • Lambda（関数の作成・更新）
    • DynamoDB（テーブルの作成）
    • Cognito（ユーザープールの作成）
    • API Gateway（APIの作成）
    • CloudFront（配信の作成）
    • Route53（DNSレコードの作成）
    • ACM / AWS Certificate Manager（証明書の発行）

    確認方法: AWSマネジメントコンソール右上のユーザー名をクリックし、「セキュリティ認証情報」を開くか、IAMサービスの画面で自分のIAMユーザーを開いて「アクセス許可」タブを確認します。上記10個のサービスすべてに対する権限が個別に付与されているか、またはAdministratorAccessという1つのポリシー（このAWSアカウント内のほぼ全サービスをまとめて許可するポリシー）が付与されていれば、上記すべての権限を満たします。このプロジェクトを最初に構築した際は、initial-admin-user-018811607892というIAMユーザー（AdministratorAccessが付与済み）を使用しました。

  8. Stage 7

    Excel出力の動作確認

    出力先: AWSS3バケット employee-renrakusaki-data の export/ フォルダ配下。Stage 4以降いつでも実行できます。取込のようなS3イベントによる自動トリガーはなく、管理者がemployee-renrakusaki-ExportCsv関数を手動実行するたびに、その時点のDynamoDB全件をExcelブック（.xlsx）として書き出します。出力ファイル名は employee-renrakusaki_YYYYMMDD_HHMMSS.xlsx、21列すべてを文字列（セル書式「文字列」）として書き込むため、番地（例: 20-6）や電話番号（先頭の0）などもExcelで直接ダブルクリックで開いた時点でWEBに入力された内容のまま表示されます（CSVで出力していた頃は、Excelが列の値を日付や数値だと自動判定して見た目を変換してしまう問題がありました）。取込用CSVとは別形式のため、出力したファイルをそのままincoming/へ再アップロードして再取込することはできません。

    操作方法（コンソール）

    1. AWSマネジメントコンソールで Lambda を開く（リージョン: ap-northeast-1 東京）
    2. 関数一覧から employee-renrakusaki-ExportCsv を選択
    3. 上部の 「テスト」 タブを開く
    4. イベントJSONは空の {} のままで、右上の 「テスト」 ボタンをクリックして実行
    5. S3 サービスを開き、employee-renrakusaki-data バケットの export/ フォルダを見ると、実行時刻を含む新しいExcelファイル（.xlsx）が生成されている
    6. そのファイルを選択して「ダウンロード」→ ダブルクリックしてExcelで開く

    操作方法（CLI）

    # 手動実行。生成されたS3キー（bucket/key）が結果として返ってくる
aws lambda invoke \
  --function-name employee-renrakusaki-ExportCsv \
  --region ap-northeast-1 \
  /dev/stdout

# 上のkeyの値を使ってダウンロード（例）
aws s3 cp s3://employee-renrakusaki-data/export/employee-renrakusaki_20260917_154006.xlsx \
  ./employee-renrakusaki_export.xlsx \
  --region ap-northeast-1
